## Handler order

1. **Bind transport identity.** Route-bound stable operation IDs populate the typed command. Reject missing, empty, malformed, or conflicting route/body identities. MCP supplies the same required typed value. Never generate a replacement ID. Keep logical command identity separate from execution-attempt identity.
2. **Authenticate and authorize.** Resolve tenant and actor from authenticated context, apply the command's declared authorization policy, then validate tenant/owner scope. Do this before querying prior intent so retries cannot reveal unauthorized result data.
3. **Normalize authored intent.** Compute the canonical command intent from the typed business fields, excluding transport metadata, attempt IDs, timestamps generated by infrastructure, while retaining every authored expected revision/epoch/version. The primary expected revision is also compared explicitly under its named owner scope. Preserve actor, target owner, lifecycle episode/generation, command kind, and original expected revision as comparison fields.
4. **Resolve retry from authoritative owner facts.** Resolve the authoritative atomic native binding by realm/logical ID, authorize its concrete resource scope, then read the complete selected native fact set. A projector miss cannot prove absence; [native acceptance](native-acceptance-contract.md) supplies uniqueness and concurrency semantics. Resolve all accepted facts for that operation, including terminal or later lifecycle facts. Do not use a lifetime receipt dictionary or a generic receipt event.
   - Same operation identity, actor, owner, lifecycle episode, kind, canonical intent, and original expected revision: return the original first write status/body without append. Asynchronous writes retain their original 202 even after completion; authorized status/result GETs expose final outcome.
   - Same identity with any changed comparison field: return Conflict.
   - No prior accepted operation: continue as a new command.
5. **Validate new-operation guards.** Check expected owner revision/OCC, local invariant, legal lifecycle transition, and exact immutable source proofs. Prove temporal freshness where policy requires it. Do not pass live aggregates across stream boundaries. A source proof identifies owner, event/position, source revision, digest, and required business facts.
6. **Append business facts atomically to the owner.** Check serialization and complete attributed-batch limits before opening append. Persist only accepted business decisions; do not append worker attempts, cursors, leases, or transport outcomes as domain facts.
7. **Dispatch reactions after append.** A reactor receives a committed source fact and creates a typed command to its target owner. Its operation identity is deterministic from source event, effect kind, target owner, and lifecycle episode. Target handlers use the same authorization/proof/retry rules. Reactions are at-least-once; exact replay returns the accepted result, proven supersession is a terminal no-op, dependency failure retries, and conflicting intent or invalid proof is quarantined for repair.
8. **Recover unknown outcomes by reading authority.** After timeout, crash, or unknown append result, re-read the authoritative owner using the same operation identity. Never infer failure from absence in a stale projection, release a reservation because of elapsed time, or issue a new identity for a retry.

## Guard layers

| Layer | Responsibility | Examples |
|---|---|---|
| Authorizer / transport | Caller identity, tenant scope, route shape, command policy | tenant member, scoped administrator, independent reviewer |
| Handler / choreography | Retry equivalence, lifecycle episode, cross-owner proof, freshness, reservation protocol | exact accepted service epoch, complete import publication, withdrawal fence |
| Aggregate | Invariants decidable from its own state and supplied immutable proofs; revision concurrency | one active claim, monotonic generation, immutable approved version |

An aggregate must not repeat authorization rules or perform a read/modify/write against another aggregate. A handler must not treat an authorizer decision or a projection row as a durable source proof. Where one decision requires multiple owners, persist accepted intent and recover forward through explicit reservations and proof-carrying commands.

## Required invariant regressions

For each operation family, keep focused tests for:

- exact retry after subsequent edits, removal, reinstatement, closure, or a new lifecycle episode;
- same identity with changed actor, owner, episode, command kind, canonical input, or expected revision returns Conflict;
- missing/malformed/mismatched route identity is rejected; route, MCP, queue and reactor preserve one logical identity;
- stale expected revision is rejected only for a new operation; exact original retry returns its original result;
- stale, wrong-owner, wrong-event, wrong-digest, incomplete, or superseded proof cannot authorize a mutation;
- append timeout/crash and projection lag recover from authoritative facts without duplicate append;
- delayed receiver commands cannot undo a later generation or release a newer reservation;
- every business event is emitted by exactly one owning aggregate; technical progress and external-effect outcomes remain process state.
