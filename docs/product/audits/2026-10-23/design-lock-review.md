## Jev review and naming decisions

The [first bounded comparison](design-lock-review-jev-request.json) and [response](design-lock-review-jev-response.json) favored campaign admission (0.95), program-first readiness (1.00), gap-first links (0.95), personal delivery recording (1.00), named resolved durable intents (1.00) and explicit current-source uses (1.00). The [edge comparison](design-lock-edge-review-jev-request.json) and [response](design-lock-edge-review-jev-response.json) favored prepare/protect/accept recovery (0.96), presence-preserving canonical DTOs (1.00), valid global selector tokens (1.00) and fixed first responses/status queries (0.98).

Use the selected owner names already present in the catalogs: ProviderRiskAcceptance, ServiceEngagementIndependence, ProgramReadiness, AuditPackageManifest, AuditPackageDelivery and ArtifactDownloadGrant. Admitted means recoverable request authority; Authorized means complete executable policy authority; Materialized means the independent native child exists. These names cannot be interchanged. Protected recovery acceptance requires full protections; package delivery remains recording. Earlier weak Jev preference for retaining the readiness ledger is recorded in implementation-decisions.md; compact ProgramReadiness preserves its atomic latest/decision conflict set while separating histories. Model confidence is advisory; source counterexamples and ordered invariants determine adoption.

The [boundary-correction comparison](boundary-correction-jev-request.json) and [response](boundary-correction-jev-response.json) (jev-1.14.0) screened the corrections adopted after the merged baseline review: route-determined guard-first admission with the neutral TenantManagerSourceMutationAdmitted fact (1.00 over member-stream eligibility uses, the prior read-guard-then-append design and a guard for every member mutation), per-first-owner write acceptance with the realm-wide index scoped to status/result routes and cross-route duplicates (1.00 over blocking all paths or resource-scoped status routes), no ExpectedRevision on token consumption (1.00), one normative process record owning receiver dispatch order (1.00), the explicit allowlist for the six shipped ulong commands (1.00) and the (campaignId, personId) participant key (1.00). Two yes/no screens were weaker: that the guard correction makes a suspended or removed episode impossible to count available after a concurrent registration (0.81), and that per-first-owner acceptance is sufficient for every write path (0.68). Both are advisory. The guard claim rests on LOCK-08 steps 6–7, which must pass before the ACCESS-01 slice closes; the acceptance claim rests on every first owner being route-determined, which the validator cannot prove and the implementation review of each owner slice must confirm.

The [reservation-order comparison](reservation-order-review-jev-request.json) and [response](reservation-order-review-jev-response.json) found one last contradiction: practice acquire required the epoch-grant event, forcing an acquisition order regardless of stream-key sort. Adopt original immutable root admission as Source for every temporary grant, then require the full exact grant set at irreversible authorization (Jev 1.00). LOCK-20 tests practice keys sorting before epoch and reversed authored ordering. No stream renaming workaround or unsorted exception is required.
