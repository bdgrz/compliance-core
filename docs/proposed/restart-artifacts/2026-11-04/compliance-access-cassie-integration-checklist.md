## Ready scope and blocking decisions

- The six Team/Role directory repositories are persistence implementations for retained approved owners. `RoleTeamDirectory` is the reverse read index of TeamRole, not a seventh aggregate. They can be integrated as current-runtime persistence work, with the schema/DI and fixtures below.
- `CassiePermissionAuthorizer` is both an authorization implementation and the graph explanation projection (`IPermissionProjection`, `IPermissionAuthorizer`, `IMemberAccessReader`). Switching it has wider transitive unit reach than the six directory readers. It is not an optional presentation dependency.
- This lane does not implement target PA-01/02/03/12/17/18: it preserves the old graph, built-in-only filtering, unscoped TeamRole identity and old runtime authorizers. Report it as native persistence migration, not platform-access completion.
- Confirmed integration blockers: production shared DI still names removed types; global application schema omits eight access tables; three unit fixture families directly name removed types; one paged-contract fixture throws the old exception; one excluded E2E fixture still has a compile-time removed-type reference.
- Root owns all shared changes. Do not mechanically replace every Fitz access-related store: several belong to explicitly superseded owners.

## Transitive SQL paths: source-backed reach and fixture triage

1. Native `CassiePermissionAuthorizer.IsAllowedAsync:66–85` validates request and projected membership, then opens SQL for any matching active `client_personnel` membership. Empty in-memory KV is no longer a harmless empty permission graph: without a native lease/schema this becomes a SQL connection/relation failure. Inactive/foreign/firm-staff membership can return false before SQL. `IMemberAccessReader.ReadAsync` always opens SQL after being called. Do not infer a fixture requires native DB merely because it calls AddCompliance.
2. `AccessGrantPermissionAuthorizer.cs:67–71` depends separately on `ITeamMemberDirectoryReader` and `IRolePermissionDirectoryReader`. In `GetEligibleGrantsAsync` it reads role permissions only for eligible matching grants and team membership only for team principals. A fake `IPermissionAuthorizer` does not replace these dependencies. Production aliases at composition root 844–850 cover **three distinct interfaces** (`IAccessGrantPermissionAuthorizer`, scope authorizer, role authorizer). Replacing only one interface does not replace the other two.
3. `AccessGrantProposalValidator.cs:56–79` reads RoleDirectory for any well-formed grant proposal; team principal validation also reads TeamDirectory. Fixtures creating real legacy grants require native directory catchup even if their request authorizer is controlled.
4. `GetMemberAccessHandler.cs:55–59,89–111` reads the graph and Team/Role names; later team-grant and permission explanation branches read TeamMember/RolePermission. This endpoint's explanation is its subject. It needs real graph fixtures where projection behavior is asserted, not an optional-name fake to avoid SQL.
5. `ListTeamMembersHandler.cs:39–42,69–81` first reads the native TeamMember directory, then optionally enriches member display through events/membership/email/profile/Person. Optional Person display is distinct from the authoritative TeamMember directory. `GetTenantMemberHandler` and `ListTenantMembersHandler` use Person enrichment but do not themselves read the seven new access repositories.
6. `FieldRestrictions.ForActorAsync` always invokes the supplied permission authorizer; GetPerson/GetWorkRelationship/source observation/snapshot handlers can therefore open authorization SQL even when their main reader is mocked. These field permissions are security behavior, not optional presentation. Existing focused tests that explicitly control IPermissionAuthorizer should remain controlled.
7. Production `ApplicationInventoryAuthorizer` and `TechnologyInventoryAuthorizer` first call IPermissionAuthorizer after active membership/tenant guards; their restricted-visibility services can then call the separately registered scoped authorizer. Redaction authorization, tenant reads/activation, RBAC management, workforce, waiver/retention and restricted compliance-record visibility also use IPermissionAuthorizer. Keep source eligibility and final source-member checks; do not change authorization logic as a migration shortcut.
